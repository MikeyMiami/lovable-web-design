# Telnyx Provider — dual-provider build + per-client provisioning

Telnyx is the SECOND provider, built 2026-07 alongside TextGrid because TextGrid's voice path has a **confirmed, unfixable caller-side ringback defect** (all four `<Dial>` ringback attributes ignored on genuinely-served TwiML — see `docs/VOICE-RINGBACK-TEST-RESULTS.md`). Telnyx has native ringback (SIP 183 early media / 180), full public docs, complete provisioning APIs, ~$0.004 SMS / ~$1 numbers on **pay-as-you-go**. **Design intent: Telnyx more than likely REPLACES TextGrid entirely later** — the code is written along that grain (§9 endgame). Plan of record: `docs/TELNYX-PARALLEL-BUILD-PLAN.md` (audited 2026-07-15) **as revised by the single-account correction (this section + §1)**.

> **⚠️ MODEL CORRECTION (2026-07-15): NO Managed Accounts.** The original plan used a Telnyx Managed Account per client. **Managed Accounts require a $1,000/month commit plan** (not available pay-as-you-go) and buy only things we don't need (API-key isolation from third parties we don't have, per-client Telnyx invoicing we don't use, client portal logins that never happen). Telnyx support confirmed (2026-07-15): one pay-as-you-go account supports **multiple 10DLC brands (different EINs), separate campaigns per brand, up to 49 numbers/campaign, multiple messaging profiles**. Their stated recommendation for a sole-operator ISV: **one account-wide API key, separate clients by messaging profile, map number→client in your own DB** — which is exactly our `clients` table. 10DLC rules unchanged: each end-customer needs their own brand; numbers can't be shared across brands; each brand needs its own campaign(s).

## §0 — Dual-provider model (what routes where)

- **`clients.provider`** (`'telnyx'` default | `'textgrid'` legacy) — the per-client switch. All outbound routing keys off it. Flip = one field, instantly reversible. **Telnyx is now the go-forward DEFAULT and the ONLY provider selectable for new clients** — the column default flipped `'textgrid'`→`'telnyx'` (new migration) and admin's Messaging Provider select is Telnyx-only. TextGrid is FROZEN LEGACY: it still routes any client already on `'textgrid'`, but is not the default and cannot be chosen for new clients.
- **Parallel columns (J3):** Telnyx identity lives in its OWN columns — `telnyx_number`, `telnyx_messaging_profile_id`, `telnyx_texml_app_id`, `telnyx_brand_id`, `telnyx_campaign_id`, `telnyx_a2p_status` (reuses the `a2p_status` enum). *(The former `telnyx_managed_account_id` / per-client `telnyx_api_key` columns are REMOVED — single-account model.)* TextGrid columns are NEVER overwritten — both configs coexist; the old TextGrid number keeps receiving inbound during migration (STOP tail).
- **TextGrid is FROZEN** during the dual window. Freeze means freeze: any TextGrid change is an explicit, logged exception. Bugs found in shared logic are fixed in `_shared/` only; divergence noted, never back-ported.
- **Inbound needs no provider sniffing:** Telnyx numbers point at the `telnyx-*` edge functions; TextGrid numbers at the original four. Separate URLs, separate signature schemes — they never meet.
- `messages.twilio_sid` holds the Telnyx message id (`data.id`) — same column, same dedup indexes.
- **Pre-flip asymmetry:** once a Telnyx number is provisioned but `provider` is still `textgrid`, inbound on the Telnyx number ALREADY processes (lookup is by `telnyx_number`, deliberately — enables pre-flip canaries) while outbound still leaves from TextGrid. Harmless unless the Telnyx number is published before flip — don't publish it.

## §1 — Credentials & the trust boundary

- **`TELNYX_API_KEY`** — the ONE account-wide API key (all sends + provisioning ops). Cloud secret, non-VITE. *(Renamed from `TELNYX_MASTER_API_KEY` — "master" implied a manager/sub-account hierarchy that no longer exists.)*
- **`TELNYX_PUBLIC_KEY`** — the account's Ed25519 webhook public key (portal → Keys & Credentials). ONE per account; `provider_webhook_secret` is unused on the Telnyx path.
- **No per-client credentials.** Per-client separation is **app-logic-level**, not Telnyx-enforced.
- **🔒 TRUST BOUNDARY (security-relevant, test accordingly):** with one shared key, client isolation lives entirely in our code. Two paths ARE the boundary: (1) **outbound `from`-resolution** — the runner/reply/test-sms resolve `from = clients.telnyx_number` per client; a bug here sends from the wrong client's number; (2) **inbound number→client lookup** — `.eq("telnyx_number", normalizeE164(to))` in every telnyx-* handler; a bug here crosses client data. Both must be covered by fixtures: unknown-number (clean `no_client` branch, no writes), wrong-number, and cross-client (two clients with telnyx_numbers → writes land on the right one). This is the standard single-account ISV posture.

## §2 — Outbound SMS (`sendViaTelnyx`)

`POST https://api.telnyx.com/v2/messages`, JSON, `Authorization: Bearer <TELNYX_API_KEY>` (the one key, from `getTelnyxConfig()` — callers do NOT resolve per-client auth for Telnyx):
`{ from: <clients.telnyx_number>, to, text, webhook_url: <telnyx-sms-status URL>, use_profile_webhooks: false }`
- **The `from` number IS the client identity** on Telnyx's side (trust boundary §1).
- Success: `json.data.id` → `sid`; map into the UNCHANGED `SendResult` contract (`{ok:true,sid,status} | {ok:false,retryable,error}`).
- Failure: `json.errors[]` → `[{code,title,detail}]` (NOT Twilio numeric codes) → error string. Log full errors array during canary.
- **`optout_blocked:<code>` (D13):** if the error class = Telnyx suppression-list / recipient-opted-out, return that distinguishable string; the RUNNER (caller) treats it as authoritative — sets `contacts.opted_out_at` + exits enrollments. Identify the exact code class at Day-0 canary.
- Stub mode (`SMS_MODE=stub`) identical to TextGrid: `STUB-<uuid>`, no network. Unrendered-`{token}` guard applies the same.
- **Reactivation runs on the CLIENT'S OWN Telnyx number [2026-07-21 — the J4 "TextGrid-only pool" ruling is OBSOLETE].** The agency number pool was REMOVED; the "Upload Customers" flow now enrolls into the per-client `reactivation` drip delivered by the NORMAL runner from `clients.telnyx_number` (throttled + a REQUIRED consent attestation) — same `from`-resolution as every other per-client send, no pool, no separate creds. (Optional future re-isolation via a dedicated `telnyx_reactivation_number` is a documented not-built seam — see `/features` + `docs/reactivation-number-pool-spec.md`.)

## §3 — Webhooks (the four `telnyx-*` edge functions)

Native webhooks are **JSON** (`data.event_type` + `data.payload.*`), signed **Ed25519**: headers `telnyx-signature-ed25519` (base64) + `telnyx-timestamp`; signed message = `"{timestamp}|{rawBody}"`; verify vs `TELNYX_PUBLIC_KEY`; ~5-min replay window (timestamp UNIT verified at Day-0 — code tolerates s or ms).
- `telnyx-sms-inbound` — verify → parse `message.received` → **normalizeE164 both numbers regardless** → client lookup by `telnyx_number` **(= the inbound trust boundary, §1)** → SHARED CORE (contact/conversation/message dedup/intent/reply-exit — identical behavior to TextGrid's inbound).
- `telnyx-sms-status` — `message.sent`/`message.finalized` per-recipient status → `messages.status` by `twilio_sid = payload.id`. **Terminal-wins guard:** never downgrade delivered/failed/undelivered to a transient (events can arrive out of order).
- `telnyx-voice-inbound` / `telnyx-voice-status` — §5.
- **⚠️ CONFIRMED CALLBACK REALITY (2026-07-20, from real Telnyx payloads):** voice callbacks are **form-encoded, Twilio-CapitalCase params, E.164 with `+`** (Q2 answered); they DO carry `telnyx-signature-ed25519` + `telnyx-timestamp` (Q1 — voice can hard-verify once the real key is set; until then soft-verify shows `sig_mismatch` against the TEST key, expected). **THE GOTCHA:** on the **Dial-action callback** (the one with `DialCallStatus`), Telnyx sends **`To` = the FORWARD number (`call_forwarding_number`), NOT the business `telnyx_number`** — so a `telnyx_number` lookup FAILS and real misses (busy/no-answer) get dropped as `no_client`. **FIX (deployed):** `telnyx-voice-inbound` puts `?client=<id>` on the `<Dial>` action + amdStatusCallback URLs; `telnyx-voice-status` resolves the client by that param (telnyx_number fallback for the progress/cost callbacks, which DO carry `To`=business number). Ed25519 signs `{ts}|{body}` NOT the URL, so the query param is signature-safe (unlike TextGrid's URL-in-HMAC). Telnyx fires MULTIPLE callback types keyed by `CallbackSource`: `call-progress-events` (CallStatus/HangupCause), `call-cost-events` (pure cost noise — **short-circuit before miss logic**), and the Dial-action callback (DialCallStatus + XmlRequestUrl). SHAKEN/STIR on inbound = `ShakenStirAttestation=a` (A-level — calls won't be spam-labeled). **AMD (voicemail detection) LIVE-VALIDATED 2026-07-20 on TeXML — the exact recipe:** `machineDetection` goes on the **`<Number>` noun, NOT `<Dial>`** (`<Dial machineDetection>` and `amdStatusCallback` are silently ignored — they are NOT real TeXML attributes). Wire it as `<Number machineDetection="Enable" detectionMode="Premium" statusCallback="<STATUS_URL>?client=<id>" statusCallbackEvent="answered amd completed">`. The AMD result arrives as a **separate webhook carrying ONLY `CallSid` + `AnsweredBy`** (values: `human | machine_start | machine_end_beep | machine_end_silence | machine_end_other | fax | unknown`) — no `CallStatus`/`To`, so it MUST be handled BEFORE any field-validation guard or it dies as `bad_fields`. The AMD webhook rides the **PARENT (caller-facing) CallSid**. Because each webhook is a separate invocation, PERSIST it (event `telnyx_amd_result` {call_sid, answered_by, client_id}); on the terminal event correlate by `CallSid OR ParentCallSid OR DialCallSid`. Precedence: `answered_by` startsWith `machine` → **MISS even when dial_status=completed** (`rule=amd_machine`); `human` → **suppress** (`rule=amd_human_override`); else dial_status rule {no-answer,busy,failed,canceled}. Proven live: answered→`no_miss`/amd_human_override, decline-to-voicemail→`missed_fired`/amd_machine. Costs Regular $0.002 / Premium $0.0065 per call. Dial `timeout=45` so the carrier voicemail answers naturally (no cold hangup). **⚠️ Miss DOUBLE-fires** (parent + forward leg both correlate to the one AMD result) → the `fireMissedCall` throttle/enroll MUST key on **(client_id, caller From) only**, never on To, or the customer gets two textbacks.
- **Capture-first (non-negotiable):** every handler opens with an unconditional raw-capture debug event (`telnyx_*_debug`) + a branch event before every return (`telnyx_*_branch` incl. the served response). **TeXML webhook signing is UNKNOWN (Q1) → voice handlers SOFT-VERIFY (log-only, never hard-401 on an assumption)** until Day-0 capture confirms. The SMS-saga lesson, institutionalized.
- **Shared core (J2):** handlers import `supabase/functions/_shared/core.ts` (+ `telnyx.ts`) — written NEW to byte-match the frozen TextGrid functions (proven empirically 2026-07-15: 8/8 fixture suite). **Handlers must literally `import` from `_shared/` — grep after every publish; no inline copies.**
- **Opt-out ownership (J5/D10):** Telnyx messaging-profile auto-opt-out is DISABLED — the app's STOP/STOPALL/UNSUBSCRIBE/CANCEL/QUIT/END + whole-word `pass` (+ START/YES/UNSTOP) logic is the single source of truth. Day-0 STOP canary must produce exactly ONE confirmation. Opt-out is **contact-level and provider-agnostic**: a STOP via the TextGrid path suppresses Telnyx sends (same `contacts.opted_out_at`).

## §4 — Per-client provisioning runbook (manual v1; API automation = Phase 2) — 5 steps

1. Register the **10DLC brand** for the client (their EIN / legal name / **legal business address** (`clients.legal_address` — the registered address from the client's IRS documents; may differ from the public site address) / vertical — reuse the wizard's captured fields) → `telnyx_brand_id`.
2. Register the **campaign** under that brand — reuse the `/a2p-site-compliance` generated pack VERBATIM (same TCR registry; the pack that passed on TextGrid) → `telnyx_campaign_id`, `telnyx_a2p_status`. **~3–7 business days — START AT SIGNING (the real clock).**
3. Buy a **local number** (~$1/mo; account **L2 verification** required once, globally) → `telnyx_number`.
4. Create a **Messaging Profile** (inbound webhook → `telnyx-sms-inbound`; **auto opt-out OFF**) → `telnyx_messaging_profile_id`; assign the number to the profile **AND the approved campaign** (~2h propagation; no A2P traffic before it completes).
5. Assign the number to the **SHARED TeXML app** (ONE app account-wide — created once at Day-0: Voice URL → `telnyx-voice-inbound` POST; Status Callback → `telnyx-voice-status`; all clients' handlers resolve the client by `To`, same pattern as the shared SMS webhooks). Store the shared app's id in `telnyx_texml_app_id` (same value on every client row — the column means "the app this client's number is assigned to" and keeps per-client apps possible later, e.g. per-client failover URLs). Then flip `clients.provider='telnyx'` — everything routes automatically; flip back = one field.

*(Former steps "create Managed Account" + "mint MA API key" are DELETED — single-account model.)* Phase-2: steps 1–5 are all API-covered → automate in onboarding later (the thing TextGrid never allowed).

## §5 — Voice (TeXML) + missed-call detection

TeXML webhooks arrive in **Twilio format** (CallSid/From/To style — normalize anyway; capture-first). Response TeXML **[CORRECTED + LIVE-VALIDATED 2026-07-20 — AMD lives on `<Number>`, NOT `<Dial>`; see §3 for the full callback-handling recipe]**:
`<Response><Dial timeout="45" callerId="{ORIGINAL CALLER From}" action="{telnyx-voice-status URL}?client={id}" method="POST"><Number machineDetection="Enable" detectionMode="Premium" statusCallback="{telnyx-voice-status URL}?client={id}" statusCallbackEvent="answered amd completed">{call_forwarding_number}</Number></Dial></Response>`
- ⚠️ `<Dial machineDetection>` + `amdStatusCallback` are **silently ignored** by Telnyx (they are NOT real TeXML attributes — the source of the first "AMD never fired" bug). AMD MUST ride the `<Number>` noun and the result is delivered to the `<Number>`'s `statusCallback` when `statusCallbackEvent` includes `amd`. `?client={id}` on BOTH callback URLs is mandatory: the Dial-action callback's `To` is the FORWARD number, so a `telnyx_number` lookup fails without it. `timeout=45` lets the carrier voicemail answer naturally (no cold hangup).
- **callerId = the ORIGINAL CALLER's number [LOCKED, LIVE-VALIDATED 2026-07-20]** — `esc(from)` (the normalized inbound `From`), NOT the business `telnyx_number`. Telnyx PERMITS caller-ID passthrough on forwarding (unlike the old TextGrid build-spec decision-3 which used the owned number to dodge rejection). Confirmed: owner's phone shows who's actually calling AND a callback dials the customer (not a loop to the owner's own line). If a future provider/carrier rejects the un-owned callerId (call stops connecting), fall back to `telnyx_number` + a `<Number url>` whisper announcing the caller.
- **⚠️ Telnyx VOICE = the WRONG app type will silently fail:** the number's Voice MUST be on a **TeXML Application** (executes our returned XML), NOT a **Voice API / Call Control Application** (JSON command paradigm — it ignores our TeXML `<Dial>` response → call rings but never forwards). One number → one voice app. Also keep Telnyx's NATIVE "enable call forwarding" checkbox OFF (it intercepts before the webhook — the TextGrid trap).
- **Ringback is native** (183 early media / 180 ringing) — ✅ **LIVE-VALIDATED 2026-07-20: rings + forwards + real caller ID, all working first real call.** The Day-0 LISTEN TEST was the go/no-go gate; PASSED. No `<Say>` bandage.
- `telnyx-voice-status` handles BOTH the Dial **action** callback and the **AMD** callback. **Miss rule + precedence (LOCKED, fixture-proven 2026-07-15):** AMD=**human** overrides everything → never fire missed (incl. the cross-webhook `amd_human_prior` correlation by CallSid). AMD=**machine** → fire missed EVEN on `DialCallStatus=completed` (the voicemail-answers case TextGrid provably couldn't detect). Else missed := `DialCallStatus ∈ {no-answer, busy, failed, canceled}`. → shared `fireMissedCall` (60-min throttle unchanged).
- **AMD is ASYNC + non-blocking [RESOLVED 2026-07-20]:** the `<Number statusCallback>` AMD event fires in parallel and does NOT gate the bridge — the caller reaches the owner/voicemail normally while AMD classifies. The result is a SEPARATE webhook with only `CallSid` + `AnsweredBy` (no `CallStatus`/`To`) → handle it BEFORE any field-validation guard (else `bad_fields`), PERSIST it (event `telnyx_amd_result`), and on the terminal event correlate by `CallSid OR ParentCallSid OR DialCallSid`. ⚠️ The miss can DOUBLE-fire (parent + forward legs both correlate) — the `fireMissedCall` throttle keys on `(client, caller From)` and is fine sequentially, but make the claim atomic (conditional UPDATE compare-and-swap) to close the same-millisecond race. No duration heuristic needed — real AMD works.
- No `call_forwarding_number` → missed_say TeXML + `fireMissedCall` (same as TextGrid behavior).
