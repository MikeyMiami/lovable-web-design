# Agency View — cross-tenant agency dashboard at `/agency`

The agency-wide layer above the per-client `/admin`. **All-clients scope** (no single active client), gated to `admin`/`agency_owner`. It exists so the agency sees what needs attention across EVERY client without drilling into each, and controls payment access from one place. **[BUILT — Phase C-1, 2026-06-20; app-layer on `golden-master-v1.7`, no migration.]**

**Distinct from `/admin` [LOCKED].** The per-client `/admin` shell scopes to ONE active client (the client selector + `useActiveClient`). The agency view is deliberately a **separate `/agency` shell** because it is cross-tenant — mixing the two would fight the active-client model.

## Role model + access gate
Agency-scoped surface (`admin`/`agency_owner` — `is_admin()` covers both). The shell role-gates via `user_roles` (a `client_owner` hitting `/agency` sees "Not authorized"). **NEVER payment-gated** (the `access_suspended` gate suspends only the client PWA).

## Surfaces
- **Shell** (`src/routes/_authenticated/agency.tsx`): role-gate + a **5-tab** nav (**Pending** · **Onboarding** · **SEO Status** · **Payment Access** · **Demo Clients**) + an `<Outlet/>` + a "← Admin" link back to `/admin`. *(Was described as 3-tab — corrected 2026-07-29: SEO Status and Demo Clients were added later.)* **Pending** carries a **count badge** = open/in-progress tickets; **Onboarding** carries a **count badge** = `clients` with `status='pending'` (both 15s poll).
- **Pending queue** (`agency.index.tsx`, `/agency`): the cross-tenant attention queue — all `open`/`in_progress` **edit-request + support tickets across every client**, client-labelled (joined `clients(business_name)`), newest by `last_message_at`, **15s poll**. Each row's **"Open"** action routes into that client's per-client admin thread: it writes `localStorage["admin.activeClientId"] = clientId` (the `/admin` shell's `STORAGE_KEY`, read on mount) then navigates to `/admin/edit-requests` or `/admin/support` by `kind`. **Route-only — no inline reply** (replies/approvals happen in the per-client admin surface; the queue just routes there).
- **Onboarding queue** (`agency.onboarding.tsx`, `/agency/onboarding`) **[BUILT — C-3c-2c]**: the cross-tenant **pending-onboarding** queue — all `clients WHERE status='pending'` (not deleted), newest by `created_at`, client-labelled (business_name + slug), **15s poll** + a count badge. Each row also carries a **"Decline"** action **[BUILT 2026-07-22 — decline = PERMANENT FULL PURGE]**: confirm-guarded → `declineOnboardingClient` server fn (admin-gated; **hard guard: refuses unless `status='pending'`**) → deletes the client's storage prefixes (`client-assets/{id}/` incl. onboarding-submission.json, `public-assets/{id}/` + any token `draft_id` prefix) → hard-DELETEs the clients row (19 FK cascades purge all data tables; `onboarding_tokens.created_client_id` + `push_subscriptions.client_id` SET NULL — token record survives). Also surfaced on `/admin/review` ("Decline & delete" beside Finalize & Invite); clears `admin.activeClientId` if the purged client was selected. NOT recoverable. Each row's **"Open"** writes `localStorage["admin.activeClientId"] = clientId` then navigates to **`/admin/review`** (the C-3c-2b Review & Finalize console — status pill + immutable submission viewer + missing-required-`template_vars` reminder + the shared `<FinalizeInvite/>`). Finalizing a client (pending→active) drops it from the queue on the next poll. Reads via the authed browser `is_admin()` RLS (`clients_select` is not status-filtered) — **no service-role**. **[BUILT — C-3d-1]** The tab also carries a **"New Client → Generate onboarding link"** card: `generateOnboardingLink` (admin server fn) mints a **one-time** token → a copyable `/onboard/$token` URL, plus an **"Email this link"** composer — editable subject/body (a default + **`localStorage`** persistence + Reset; `{link}` token) that opens the agency's own mail client via **`mailto:`** (sends from the real address = best deliverability; **no email provider/secret**). Token model = `onboarding_tokens` in `scratch-foundation`. **[C-3d-3]** Pending clients arrive in this queue from BOTH **agency self-fill** (`/onboard`) AND **client-submitted** onboarding links (the public `/onboard/$token` wizard → `/api/public/onboarding/submit`).
- **Payment Access** (`agency.access.tsx`, `/agency/access`): every non-deleted client with an `access_suspended` status pill + a **Suspend ↔ Restore** toggle → `setClientAccessSuspended`. One place to gate/un-gate client PWAs. **Excludes demo clients** (`.eq("is_demo", false)`).
- **Demo Clients** (`agency.demos.tsx`, `/agency/demos`) **[BUILT 2026-07-29]**: throwaway tenants for sales demos — show a prospect a fully branded site before they buy, with no onboarding, no A2P and no messaging config. Server fns in `src/lib/clients/demo.functions.ts` (all agency-admin gated):
  - `createDemoClient` — **only `businessName` is required**; optional address / phone / tagline / city / logo / brand colour + secondary + tertiary / services / **demo photos**. Inserts `status='active'`, **`is_demo=true`**, `demo_expires_at = now()+14d`, `allowed_origins=[]`, **no `send_settings` row, no `content_pages`, no telnyx/twilio fields**, slug **`demo-{slugify(name)}-{4 rand}`**. Does NOT reuse `insertClientFull` (no submission JSON / EIN handling). Seeds defaults (`about_us`, `differentiators`, `support_email`, `lead_form_*`, `chat_widget_*`, Mon–Fri hours, 3 generic services) so a demo never renders half-empty.
  - **Two template_vars keys are load-bearing and easy to get wrong:** services go to **`services_structured`** (`[{name,slug,description}]`) — NOT `services` — because the template's `mapPublicRowToClient` reads that key; demo photos go to **`site_assets.work_examples`** (plain `string[]` URLs), which sits ahead of the template's built-in `NICHE_DEFAULTS` stock photos in its gallery/about fallback chain. Without photos a demo shows the template's landscaping stock imagery — fine for a landscaper, weak for any other trade.
  - `listDemoClients` (soonest-expiry first) · `purgeDemoClient({clientId} | {expiredOnly:true})` — **triple-guarded**: re-read throws on a non-demo row, per-row recheck, and `.eq("is_demo", true)` on the DELETE itself. Best-effort removes the logo object; **known residue: uploaded demo photos are NOT purged** (orphan WebPs under `demo-{uuid}/site/work/`).
  - UI: create form + list with days-left badge, **"Copy slug"** (not a link — the workflow is pasting the slug into a template remix's `VITE_CLIENT_SLUG`), Delete, and "Purge expired". Optional auto-purge cron in `docs/demo-clients-build-spec.md` §7.
  - **Demos are filtered out of exactly THREE reads** (every other `clients` read is a by-id/slug/number lookup and must stay untouched): this Payment Access list, the `/admin` client switcher, and `listSeoStatus` (else every demo shows as SEO-review-due).
  - **Write safety, two layers:** `tenant-resolver.server.ts` — both `resolveTenantByOrigin` and `resolveTenantBySlug` return `null` when `is_demo` (empty `allowed_origins` alone is NOT sufficient: slug resolution never checks origins and the templates post `slug` in every form body); and template-side `isPreviewClient()` keeps forms inert on a `demo-` slug. A demo can never create a contact, enrollment, message or send — so it never reaches the runner, a cap or Telnyx.
  - Full spec + as-built record: **`docs/demo-clients-build-spec.md`**.

## Security contract [LOCKED]
- **Reads** go through the authed browser `supabase` (admin JWT → the `is_admin()` RLS branch, which returns rows across ALL clients). **NO `supabaseAdmin`/service-role in any agency route.**
- **The ONLY mutation is `setClientAccessSuspended`** (`src/lib/clients/access.functions.ts` — input `{ clientId, suspended, reason? }`; re-verifies `admin`/`agency_owner` server-side; updates `clients.access_suspended` + writes an `events` row `client_access_suspended`/`client_access_restored`). No direct `clients`/`tickets` writes from the agency UI.
- Suspending gates **only** that client's PWA shell (the already-built payment-gate intercept) — never the agency/admin surfaces, never the automations (which key off `status`/`deleted_at`).

## Relationship to the rest
- **Consumes** the B-design ticket tables (read-only here, via `is_admin()` RLS) + `setClientAccessSuspended` (v1.7). The 5 ticket write-fns + the per-client reply/approve/resolve UI live in **`admin-view`** (the queue routes into them). Data model = **`scratch-foundation`** (`tickets`) + `clients.access_suspended`.

## Build / extension notes
- **Deep-link to a specific ticket** (vs routing to the client's tab + the agency clicking it) would require threading a ticket id into `AdminTicketSurface` — deferred; v1 routes to the tab with the active client pre-set.
- **New-request flagging** = the Pending count badge + newest-first ordering (v1). A richer unread/seen model is future.
- **Cross-client overview/analytics** (status, suspended, pending counts per client as one board) = future extension of `agency.access.tsx`.
- Reachability: a single "Agency (all clients)" link in the `/admin` sidebar points to `/agency` (the only change C-1 made to `admin.tsx`).
