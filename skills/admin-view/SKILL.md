# Admin View — tabs & settings on the client website

The admin dashboard lives at `/admin` on the client website, gated to `admin` / `agency_owner` roles (RLS-scoped). It is where the agency manages this client. Build/maintain these tabs.

**Role model + access gate.** This is an agency-scoped surface (`admin`/`agency_owner` — `is_admin` covers both). It is NEVER payment-gated: the payment-access gate suspends only the client's mobile PWA (`client_owner`/`client_staff` surface), never the agency's per-client admin view or agency account. Client logins are minted by `provisionClientOwner` (scratch-foundation §5), not here.

## Tabs
- **Dashboard** (`/admin`) — KPIs (contacts in/out, sends, reviews) for the active client.
- **Contacts** (`/admin/contacts`) — CRM list + detail.
- **Conversations** (`/admin/conversations`) — full SMS inbox + threads.
- **Feedback** (`/admin/feedback`) — low-star private feedback submissions.
- **Edit Requests** (`/admin/edit-requests`) — **[BUILT — B-design Prompt 3, 2026-06-20]** per active client, the client's **Request-an-Edit** tickets (`kind='edit_request'`). List with a **Pending (default) / All / History** filter; open a thread (bubbles, `sender_side` alignment; attachments via **signed URL** from `client-assets`). **Agency lifecycle actions:** reply (`postAgencyReply` — forces `sender_side='agency'`, optional `in_progress`); **Approve / Deny — each REQUIRES a resolution** (`setTicketStatus` → `approved`/`denied` + resolution, returned to the client in-app); **Close** after implementing. **No auto re-deploy** — approve = notify + record the resolution; the agency implements the edit manually (remix / Settings).
- **Support** (`/admin/support`) — **[BUILT — B-design Prompt 3, 2026-06-20]** per active client, the client's **Support** tickets (`kind='support'`). Same shape; lifecycle = reply → **Mark in progress** → **Resolve** (`setTicketStatus`); resolved threads live under the **History** filter.
  - Both are one shared **`AdminTicketSurface`** component (parameterized by `kind`), mirroring the client PWA's `TicketSurface`. **Security contract [LOCKED]:** admin **reads via the authed `supabase` (admin JWT → `is_admin()` RLS branch) — NEVER service-role in the admin UI**; **all writes go through the role-verified service-role fns** `postAgencyReply` / `setTicketStatus` (which set `sender_side`/`status`/`resolution` authoritatively — the ticket tables are read-only-RLS + write-REVOKEd, so the UI cannot write directly). Notifications + owner-email stub fire automatically from the fns (`notify.server.ts`). **Cross-tenant** pending-edit / pending-support lists across ALL clients = the separate **agency-view** (Phase C), NOT here (this surface is per-active-client). Data model + the write boundary: `scratch-foundation` (tickets) + `mobile-app` (the client side).
- **Automations** (`/admin/automations`) — edit message templates + sequence steps (the editable surface of the automation-config content). Each drip also shows a **live count of contacts currently enrolled** (active) in it — read from `enrollments WHERE status='active'` grouped by `sequence_key`. Gives at-a-glance visibility into what's running per drip. [BUILD — new]
- **Upload Customers** (`/admin/reactivation`) — CSV/paste uploader that feeds the **Customer Review Reactivation drip** (normalize phones → dedupe → enroll, caps 50/day + 2/20min). **[DEPRECATED 2026-06-16 — superseded by the Reactivation Numbers agency pool below.** The per-client drip sends from `clients.twilio_number` and routes zero real traffic going forward; frozen code left intact; hide/repoint this tab as a UI nicety.]
- **Reactivation Numbers (agency pool)** — **AGENCY-level surface** (`is_admin`/`agency_owner`-scoped, NOT per-client): manage the pool of agency-owned, PierceWorks-approved A2P numbers — add/remove; each shows `available` or `in_use — <client>`. The reactivation CSV-upload flow picks a pool number from a **dropdown** (`available` = selectable; `in_use` = greyed + client label); selecting one assigns it to a **finite reactivation campaign** for that client (sends from the **pool number** with agency master creds, NOT the client's number), and the number **auto-releases** back to `available` when the campaign's last follow-up fires. This is the LIVE reactivation mechanism (supersedes "Upload Customers" above). Backed by net-new agency tables (`reactivation_numbers`/`reactivation_campaigns`/`reactivation_enrollments`) + a separate finite-campaign runner; **agency-scoped (`is_admin()` RLS), NOT tenant-scoped.** (Build: `docs/1f-reactivation-pool-build-spec.md`.)
- **A2P Prep (per client)** — pre-generates the business-customized Brand + Campaign copy for copy-paste into TextGrid (Brand fields, Campaign Description, Call-to-Action/consent paragraph, 5 sample messages with real values + ≥2 STOP, Privacy/Terms URLs), filled from the one token schema + the per-niche category library, with a **toggle to view the approved Review Harvest example side-by-side.** Source: `/a2p-site-compliance` (+ verbatim copy `docs/a2p-compliance-copy-source-of-truth.md`). ## Settings tab — required configurable values (per client)
- **Timezone** — drives all SMS time windows.
- **SMS Send Window** — default **09:00–19:00** in the client's timezone. Applies to MARKETING/FOLLOW-UP SMS only (review drip, one-year drip, reactivation). Purpose: don't annoy past customers.
- **Business Hours** — a SEPARATE per-client window, distinct from the SMS Send Window. Applies to the LEAD-FORM drip only: decides whether a fresh website lead gets the live in-hours response (single SMS#1) or the after-hours single message. Purpose: "is the owner reachable / open right now." Independent value from the marketing window. [BUILD — new field, and the lead-form handler must branch on it]
- **Daily SMS send cap** — customizable per client; max messages dispatched per day. Enforced in the cron runner.
- **Daily enrollment cap** — customizable per client, **default 50**; max NEW contacts entering the review drip per day. Overflow waits to the next day. Enforced at the enrollment path (mobile-app Review Request form/button + uploads). DISTINCT from the send cap — do not conflate.
- **Business identity** — business_name, tagline, phone_display, email, address, hours, license_number, logo_url, brand_color. **Logo [BUILD — upgrade]:** today `logo_url` is a paste-only text field; add a **file-upload to `public-assets`** + an **`<img>` preview + download link** so the client's logo is retrievable from their admin view (storage layer + column already exist; the upload/preview UX does not). **Brand colors:** primary = `brand_color`; secondary/tertiary = `template_vars.brand_secondary`/`brand_tertiary` — all agency-editable (a dedicated 3-color picker is a [BACKLOG] nicety; the `template_vars` JSON editor covers it today). **One branding source, two consumers:** the same brand colors + logo set here feed BOTH the marketing site AND the per-client mobile app (see `/mobile-app` → Per-client branding [BACKLOG]).
- **Social links (Brand & Site) [BUILT]** — friendly **Instagram / Facebook / LinkedIn** URL editors (pre-filled from `clients.social_links`), alongside the existing **"Social links (JSON)"** textarea. `social_links` is a dedicated jsonb column written **wholesale**, so the save **merges** the friendly fields into the full object (overlay only those keys; a blank field removes that key) and **re-seeds the JSON textarea** (dual-writer guard) — other keys (bbb/tiktok/yelp) preserved. Onboarding-captured socials (the wizard "Social Links" step → `social_links`) appear here pre-filled. The site footer renders `social_links` (new `linkedin` key = a template concern in `/website-structure`).
- **Review config** — review_place_id, review_link, star_threshold (default 4, inclusive ≥ — the Review Funnel gate), google_review_toggle (enum `review_gate_mode`: gated|direct). Toggle meaning: `gated` = use the funnel (rate page → branch by threshold; default); `direct` = skip the funnel, send everyone straight to the Google review page (no gate). The funnel logic in features applies in `gated` mode; `direct` bypasses `/api/public/r/rate`. (DB enum is 2-mode `{gated, direct}` — no separate "off"; to suppress review prompts, just don't enroll contacts.) The **Review link (Google URL) is AGENCY-SET here** (it must be formatted correctly to work — NOT collected at onboarding); saving it also **syncs `template_vars.review_request_link`** (the static message merge value) to the same URL via a merge-write (no clobber of other `template_vars`), keeping the column and the merge value identical. The client's **Google Business Profile link** from onboarding (`template_vars.google_business_profile_link`) is shown here **EDITABLE** (pre-filled, merge-safe save) so the agency can look the business up and correct it if it was entered wrong or changes.
- **template_vars** — free-form per-client placeholder values. Must cover all custom keys referenced by templates. Required set today: `company_owner_first_name`, `company_name`, `review_request_link`, `discount__on_referral`, `company_website_link`, `discount_amount`, `website_terms_page_link`, `quote_form_link` (defaults to `{company_website_link}` lander; overridable here — the page hosting the quote form), `about_us`, `services`, `differentiators` (the AI-knowledge content fields — F-complete Option A; anon-safe public content the chat bundle + site read). **NEVER put PII/secrets in template_vars — it's anon-readable via the `get_client_public` RPC projection (owner notification email is a dedicated column, not here).** Dynamic values (not template_vars, set at runtime): `caller_phone`, `call_time`, `request_time`, `message.body`, `feedback_message`, `email`. Surface missing keys to prompt the agency to fill them.
- **Returning Customer Discount (agency-set)** — a dedicated per-client Settings section for the 1-year follow-up campaign offer: **discount offer text → `template_vars.discount__on_referral`**, **discount amount → `template_vars.discount_amount`**. **Moved OUT of the onboarding wizard** (it's an agency campaign decision, not owner input). Edited via the page's direct-RLS save with a **read-merge-write** (writes the FULL `template_vars` with just these two keys overlaid — never a partial replace, which would wipe `about_us`/`services`/`site_assets`/etc.; re-seeds the JSON textarea as a dual-writer guard). Both keys stay in the required-keys "missing" flag when blank. **NOTE [LOCKED]:** any admin edit that touches `template_vars` MUST read-merge-write the full object — the server `updateClientSettings` fn and a raw `clients.template_vars` UPDATE both REPLACE the jsonb wholesale.
- **Messaging config** — twilio_number, twilio_messaging_service_sid, call_forwarding_number (the client's real phone the provider number rings through to; editable per client over time). These per-client provider (TextGrid) values are NON-secret (From + Messaging Service SID; per-client subaccount under the agency master account). The master-account auth token is a single platform runtime secret; per-client subaccount creds live in the additive `provider_*` columns. (BYO-provider/BYO-Twilio per-client creds = Option 2, future, in a server-only `client_secrets` store — not here.) `sending_subdomain`/`dkim_status` are **NOT created in v1** (deferred; `ADD COLUMN` later only if per-client email is built): owner notifications send from ONE platform-level agency sender (see Email below), not per-client domains.
- **Email sender (platform-level, NOT per-client)** — owner notifications send from ONE verified agency domain (e.g. `notify@myagency.com`) with a display name; there is no per-client sending identity in v1 (all emails go to business owners, not their customers, so per-client DKIM isn't needed). Per-client only sets the **notification recipient email** (below).
  - **Single-source rule [LOCKED]:** the provider (TextGrid) number is stored ONCE (on the `clients` row) and everything that displays or uses it READS from that single source — the marketing site (header/contact/footer, via a merge value), all SMS automations, and missed-call detection. Changing `twilio_number` in admin updates everywhere on-site + in automations automatically; never hardcode the number into a page. External placements (Google Business Profile, printed business cards) are set manually outside the system and are NOT auto-updated.
- **Notification recipient email** — the email address owner notifications are sent to. Stored in the **dedicated `clients.notification_email` column** (NOT projected by the `get_client_public` RPC — owner PII, anon-denied 42501 like `clients.email`; NOT in `template_vars`, which the RPC also defensively strips it from). Defaults to `clients.email`; resolved at send time by `resolveOwnerEmail()` = `notification_email ?? email` (single-source, same posture as `twilio_number`). Settings strips any pasted `notification_email` key from `template_vars` on write. [F-pii, 3g]
- **Marketing domain(s) / allowed origins** — agency-set; the client's site domain(s); powers the public-write CORS allowlist (see opt-in-forms / scratch-foundation).
- **Finalize & Invite (launch handoff) [BUILT — C-3c-1; moved to Review console in C-3c-2b]** — a shared **`<FinalizeInvite/>`** component on the per-client **Review & Finalize** console (`/admin/review`) — **removed from Settings** (single surface, single source) — with: the **Remix handoff checklist** (read-only — `slug`, `VITE_CLIENT_SLUG` (= slug), matched `site_style`, `allowed_origins`) + a **Finalize & Invite** button that mints the client login via **`provisionClientOwner`** (invite to the business notification email = `notification_email ?? email`; audited `client_owner` grant, `actor_source='fn'`). **Manual + idempotent**, `window.confirm`-guarded (sends a real email); admin/`agency_owner`-gated server-side; the page uses **NO service-role**. Carried config prereqs before a REAL invite: `VITE_INVITE_REDIRECT_URL` → the client-PWA set-password route + custom SMTP (default invite → spam). **[BACKLOG — UX]** the success toast isn't reliably visible on this page — add a persistent "Invited ✓" / inline success state for clear feedback on real-client invites. **[BUILT — C-3c-2a]** this action also flips **`status` pending→active** (direct-RLS update): wizard creates start `status='pending'` (dormant — no automations, not anon-visible), and Finalize & Invite activates them. **[BUILT — C-3c-2b]** a **missing-required-`template_vars`** reminder renders above it on the Review tab (shared `src/lib/clients/required-template-vars.ts` — single source, agrees with the Settings "missing keys" flag) so the agency fills gaps before inviting.

## Notes
- **All onboarding values are surfaced + editable here [LOCKED]:** every field captured by `/onboard-from-form` (business identity, review config, template_vars, timezone, site_style, social_links, messaging-provider (TextGrid)/forwarding, marketing domains, notification email, hours/business hours, service areas, discounts) must have an editor in Settings so the agency can review/adjust anything that was prefilled from onboarding. No onboarding-captured value should be invisible or uneditable in admin.
- `createClient` currently accepts only slug, business_name, phone_display, email; everything else is set here via `updateClientSettings` (or, for fields without a UI editor yet, via direct SQL until editors are added). Adding editors for those is the natural extension of this skill.
- `brand_color` is stored as hex but is NOT yet wired into the oklch theme tokens — per-client theming requires injecting a converted oklch value into the shell head (handled by the design layer, `/website-structure` §9c, which absorbed the retired `/theme-to-brand`).
- Caps and windows are the ban-protection surface: a cap or window that is only a UI field does nothing — confirm the cron runner (send cap + SMS window) and the enrollment/lead-form paths (enrollment cap + Business Hours) actually enforce these values.
