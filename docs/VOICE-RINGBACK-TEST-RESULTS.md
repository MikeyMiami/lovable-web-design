# Voice "No-Ring" — Ringback Attribute Isolation Test Results

**Date:** 2026-07-15 (UTC). **Provider:** TextGrid (Twilio-API-compatible, FreeSWITCH-based; no public technical docs; support@textgrid.com / (786) 522-1559). **Stack:** Supabase Edge Functions (Deno) responding to TextGrid's `voiceUrl` webhook with TwiML.

**Conclusion up front:** On a **genuinely-served** `<Dial>` (verified via DB instrumentation — see below), TextGrid produces **zero caller-side ringback** and **ignores all four Twilio ringback controls** — `answerOnBridge`, `ringTone`, `dialMusic="real"`, and all three combined. The caller hears **dead silence** from connect until the owner's voicemail is reached (~20s later). This is a **provider-side early-answer + no-ringback-injection defect**; there is no client-side TwiML fix within the tested attribute set.

### Prior data point — NATIVE forwarding (before app-`<Dial>` was ever wired)
Before the `voiceUrl` was wired, inbound calls were handled by TextGrid's **native number-level forward** (our function never ran — `voice_inbound_debug` had 0 rows). That path *also* produced **dead air → voicemail**. So **both** TextGrid forwarding paths — native forward **and** app-`<Dial>` with every ringback lever — produce identical caller-side dead air. This is switch-level behavior common to both, which strengthens the provider-defect conclusion.

## What this proves / rules out

- **Proven:** the app-`<Dial>` path is fully functional end-to-end (webhook wired → signature verified → TwiML served → call forwarded → owner answerable). Ringback is the *only* failure.
- **Proven:** TextGrid does not honor `answerOnBridge`, `ringTone`, or `dialMusic` (individually or combined) on `<Dial>`. No caller-side ringback is generated by any of them.
- **Ruled out (from earlier passes):** wiring/endpoint mismatch (URLs verified; `voice_inbound_debug` lands), the `To`-normalization bug (fixed; client resolves), native-forward interception (native is OFF; branch=dial), signature gating (signature verified — branch reached `dial`, never `bad_sig`), a leading media verb forcing early answer (`<Dial>` is the first/only verb).
- **Inference:** because `dialMusic="real"` was ignored, TextGrid almost certainly ignores the `dialMusic` attribute entirely — so a custom `dialMusic="<mp3 url>"` was NOT tested (it would be ignored too).

**Mechanism (best model):** TextGrid answers the caller's inbound leg immediately at `<Dial>` (SIP `200 OK` up front) and bridges to the dialed leg **without generating or relaying any ringback** — so the caller's carrier stops its own ringback (leg is "answered") and TextGrid injects none → dead air until the owner picks up (or voicemail answers). On its FreeSWITCH engine this is the classic "answered A-leg bridged with no ringback configured" case.

---

## Precise fix demand for TextGrid support

TextGrid must do **one** of the following on inbound calls handled via `voiceUrl` `<Dial>`:

1. **Honor `answerOnBridge`** — do NOT send `200 OK` on the caller's leg until the dialed (B) leg answers; relay `180 Ringing` / `183 Session Progress` and bridge early media so the caller keeps hearing real ringback. FreeSWITCH: `bridge_early_media=true`, don't pre-answer the A-leg.
2. **OR generate ringback toward the answered A-leg during dial** — FreeSWITCH channel vars: `ringback=%(2000,4000,440,480)` + `instant_ringback=true` + `ignore_early_media=true` (or Telnyx-style `generate_ringback_tone`).
3. **OR honor `ringTone`/`dialMusic`** as Twilio/Plivo document them.

Evidence to attach: the four served-TwiML strings above (each ignored) + the dual-path confirmation (native forward also dead air).

## Options on our side if the provider won't/can't fix it

1. **Conference hold-audio ringback (real workaround, if supported):** `<Dial><Conference waitUrl="…">room-{CallSid}</Conference></Dial>` — the caller lands in a conference playing a looping ringback via `waitUrl` while we REST-originate the owner's leg into the same room; caller hears a perfect ringback loop until the owner joins, plus deterministic miss detection from the owner leg's status callback. **Requires TextGrid to support the `<Conference>` noun — untested (their docs list verbs only); one test call answers it.**
2. **UX bandage (guaranteed-deployable, not a real fix):** a brief `<Say>Please hold while we connect you.</Say>` before the `<Dial>`. It doesn't create ringback, but converts unexplained dead air into an explained wait (reduces caller hang-ups). Since TextGrid early-answers anyway, a leading verb costs nothing here.
