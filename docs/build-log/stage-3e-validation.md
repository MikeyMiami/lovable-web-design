### (original flag analysis) DETAIL-pane scoping (admin-only bleed vector)
The **list** queries are all `client_id`-scoped (safe). The **conversation thread** query is also scoped: `messages … .eq("client_id", activeClientId).eq("conversation_id", openId)` ✓ — a stale `openId` from client A under active-client B returns 0 rows (X isn't a B conversation) → empty pane, **no bleed**. **But the Contact DETAIL is reported only as "detail by id"** — if that query is `.eq("id", selectedId)` *without* `.eq("client_id", activeClientId)`, then for an ADMIN (whose RLS spans all clients) a **stale `selectedContactId` from client A would render A's contact detail under active-client B → a cross-client bleed.** Critically, **the queryKey/invalidate mechanism does NOT save you here**: a refetch of a by-id-only query still returns A's row under admin RLS. Only an explicit `.eq("client_id", activeClientId)` on the detail query prevents it.
- **CONFIRM:** the Contact detail query (and any other detail/sub-pane) includes `.eq("client_id", activeClientId)`, not id alone.
- **CONFIRM:** the open selection (`selectedContactId` / `openId`) is **reset on client switch** — else an orphaned detail pane (empty for the thread; wrong-client for a by-id-only contact detail). The live walk's discriminating test: open a contact detail + a thread on client A, switch to B → the detail pane must NOT show A's data.

## 🟢 Role-grant path (for the live admin walk) — answer
- **Bootstrap the FIRST admin via direct SQL**, not the server fn: `INSERT INTO public.user_roles(user_id, role) VALUES ('<mikey-test-uid>', 'admin');` (Supabase SQL editor / service-role). The `assignUserRole` server fn **cannot mint the first admin** — its 1d authorization matrix blocks a `client_owner` from granting `admin` (chicken-and-egg: no admin exists to authorize it).
- **Reversible:** `DELETE FROM public.user_roles WHERE user_id='<mikey-test-uid>' AND role='admin';`.
- **No self-lockout:** the grant is ADDITIVE (the user keeps `client_owner` + gains `admin`); reverting is a DELETE. (Only caveat: don't leave zero admins if something later depends on one — not a concern for a reversible test user who retains `client_owner`.)
- **Audit caveat:** this grant is **UNAUDITED** — the role-mutation `audit_log` is a Stage-3.5 item, and platform-scope grants don't hit `events` (spec §12). Fine for a throwaway test grant; for REAL admin grants, prefer doing them **after** `audit_log` lands (Stage 3.5) so they're recorded. Use the exact known test uid (granting `admin` to the wrong uid = unintended cross-client access).
