### (original) 🔴 F-pii (SECURITY — pre-freeze must-fix): `notification_email` in `template_vars` leaks owner PII to anon
Settings stores the notification recipient at `template_vars.notification_email` (default `clients.email`). **But `template_vars` is one of the 13 anon-readable columns in the §A `clients_public` view** (the whole jsonb is exposed — the marketing site reads merge values from it). So an anon `SELECT template_vars FROM clients_public` returns the **owner's notification email** — re-introducing exactly the owner-PII exposure that **§A deliberately closed for `clients.email`** (42501-denied to anon). 
- **Generalizable invariant (record it):** `template_vars` = **anon-readable merge values ONLY**; NEVER put owner PII / secrets / internal config in it.
- **Fix:** store `notification_email` as a **dedicated `clients` column** that is EXCLUDED from `clients_public` (same posture as `clients.email`/`call_forwarding_number`) — or just make `clients.email` itself the editable recipient. Then the §A "sensitive columns denied to anon" check must also cover `notification_email`.
- **Plus the read-path consistency (1f/email layer):** when the owner-email send is wired (currently `owner_email_stub`), it must READ the recipient from wherever Settings writes it (the new dedicated column), with fallback to `clients.email` — else editing it in Settings has no effect (the single-source rule, same as twilio_number).
