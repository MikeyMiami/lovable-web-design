## 🔴 F-pii (SECURITY — pre-freeze must-fix): `notification_email` in `template_vars` leaks owner PII to anon
Settings stores the notification recipient at `template_vars.notification_email` (default `clients.email`). **But `template_vars` is one of the 13 anon-readable columns in the §A `clients_public` view** (the whole jsonb is exposed — the marketing site reads merge values from it). So an anon `SELECT template_vars FROM clients_public` returns the **owner's notification email** — re-introducing exactly the owner-PII exposure that **§A deliberately closed for `clients.email`** (42501-denied to anon). 
- **Generalizable invariant (record it):** `template_vars` = **anon-readable merge values ONLY**; NEVER put owner PII / secrets / internal config in it.
- **Fix:** store `notification_email` as a **dedicated `clients` column** that is EXCLUDED from `clients_public` (same posture as `clients.email`/`call_forwarding_number`) — or just make `clients.email` itself the editable recipient. Then the §A "sensitive columns denied to anon" check must also cover `notification_email`.
- **Plus the read-path consistency (1f/email layer):** when the owner-email send is wired (currently `owner_email_stub`), it must READ the recipient from wherever Settings writes it (the new dedicated column), with fallback to `clients.email` — else editing it in Settings has no effect (the single-source rule, same as twilio_number).

## 🟥 F-complete (LOCKED-completeness gap): AI-knowledge content fields have no confirmed editor
The admin-view LOCKED rule: *every onboarding-captured field must have a Settings editor.* The onboard-from-form contract lands three fields as **"site copy + AI-knowledge" with NO pinned storage column**: **About Us** (req), **All services offered** (req — the AI chat-widget's knowledge source, §7e), **Special things / differentiators**. They are NOT in the shipped 3g column list, NOT in the required `template_vars` set, and the contract doesn't pin where they live ("store it where the §7e widget can load it"). The 2f knowledge bundle reads `business_name + template_vars` — implying these belong in `template_vars` (or a knowledge field). So:
- **CONFIRM where About Us / services / differentiators are stored, and that 3g can EDIT them.** If they're `template_vars` keys → add them to `REQUIRED_TEMPLATE_VARS` so the editor surfaces + the amber callout validates them (today they'd be free-form, unguided). If they live in a separate AI-knowledge store → 3g needs a dedicated editor (or document that AI-knowledge/site-copy content is edited in the design layer, NOT Settings — which would be an explicit carve-out from the LOCKED rule).
- **Why it matters:** without an editor, the agency can't fix the **AI chat's knowledge** or the **site copy** after onboarding — and the AI-knowledge storage is itself unpinned in the spec (an underlying ambiguity 3g surfaced). Resolve before declaring the LOCKED completeness rule satisfied.
