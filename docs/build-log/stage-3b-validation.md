## 🟥 F4 — resolved AND escalated to a NEW 1f scope item

**As-built (CORRECT for stub stage):** there is exactly ONE outbound-message insert site today — `reply.functions.ts` (RLS-scoped, authed). The **cron runner does NOT write `messages`/`conversations`** at all; its stub only logs `sms_sent` to `events`. So **there is no duplicated insert logic to consolidate** — F4's original concern (two divergent insert blocks) is moot. ✓

**But this surfaces two things that must be tracked:**

1. **Consequence — drip sends are absent from the Conversations inbox, and the 3b Open-conversation button lands on an empty thread.** Because the runner never materializes outbound texts, a contact who only received drip SMS (e.g. a **missed-call textback** recipient who hasn't replied) has **no `messages`/`conversations` row**. So the missed-call notification's **Open-conversation deeplink** (validated above) resolves to nothing in stub mode — a different "dead button" cause than the 2c `related_contact_id`-null risk (here the id is set, but the target thread isn't materialized). The button is only **fully functional once 1f materialization lands.**

2. **NEW 1f scope (more than a Twilio swap):** at 1f the runner must (a) **write each outbound drip text into `messages` + bump `conversations.last_message_at`** (thread completeness), AND (b) **extract a shared `insertOutboundMessage({clientId, contactId, body, sid, status})` helper** — an **admin variant** (cron, service-role) + an **RLS variant** (reply, authed) — reused by the runner and `reply.functions.ts`. Keep the send primitive (`sendStubSmsWithRetry`) **SEND-ONLY** (preserves the F1 pre-freeze property); materialization lives in the **callers**. This is a runner LOGIC change + a reply-path refactor, not just swapping the stub for Twilio. → recorded in spec §12 (`[BUILD — 1f]`) + `/launch-check` §D.

**🟡 Open question for you (freeze philosophy):** materialization is conversation **LOGIC** — exactly the drift-prone stuff the Stage-4 freeze is meant to lock. Deferring it to 1f means a real logic change lands **post-freeze**, and the frozen golden master ships with an incomplete inbox (drip sends invisible; missed-call Open-conversation non-functional). **Recommendation to consider:** do the materialization + `insertOutboundMessage` helper **PRE-freeze** (writing stub-status message rows now), so the frozen master's Conversations is complete and the helper is proven; 1f then only adds the real SID/delivery-status. This keeps 1f a thin swap, consistent with "freeze = logic, 1f = minimal hardening." Default per your call this turn = track as 1f; flagging the alternative so it's a deliberate choice, not a default.
