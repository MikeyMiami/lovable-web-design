## ✅ Validated against the mobile-app skill + Stage-3 requirements

- **PWA shell — MATCH.** `manifest.webmanifest` + icon + `__root.tsx` (theme-color, apple-touch-icon); `_authenticated/app.tsx` = sticky header (sign out) + fixed 4-tab bottom nav over `<Outlet />`, mobile-first. ✓ (Tab-label deviation noted as F2.)
- **Auth gate — MATCH.** `_authenticated/route.tsx` `beforeLoad` → `supabase.auth.getUser()` → redirect to `/auth` if no user; the whole `_authenticated/` subtree is gated by the layout route, **no per-child guards needed** (correct TanStack pattern — the layout route guards all children). Logged-out `/app` → `/auth` confirmed. No tenant-data route lives outside the gate (`auth.tsx` is the public login; `__root.tsx` is the shell; public data routes are the intentional `/api/public/*`). ✓
  - *Strengthening note:* `ssr:false` means the route guard runs client-side — so the guard is **UX (redirect-to-login)**, and the **real security boundary is RLS** (confirmed below). Even if the client-side guard were bypassed, queries return only the user's own rows (or none). Correct layered model per the runbook ("verify behind auth AND that RLS scopes every read").
- **Tenant isolation (the #1 cross-cutting requirement) — CONFIRMED.** Conversations queries use the **browser client** (`@/integrations/supabase/client`, publishable-key client carrying the user's JWT) — **NO `supabaseAdmin`/`client.server` import anywhere under `src/routes/_authenticated/*` or `src/lib/messages/*`** (Lovable grep-verified). DB policies enforce the scope independently:
  - `conversations_all: USING (is_admin(auth.uid()) OR client_id IN (SELECT user_client_ids(auth.uid())))`
  - `messages_all: USING (is_admin(auth.uid()) OR client_id IN (SELECT user_client_ids(auth.uid())))`
  A logged-in `client_owner`/`client_staff` sees only rows in their `user_client_ids` set; cross-tenant rows are invisible at the DB layer. **No service-role path on the read surface.** ✓ Matches the runbook's "any read surface using the admin/service-role client to fetch tenant data is a cross-tenant leak."
- **Reply write-back is RLS-checked — CONFIRMED.** `sendReply` serverFn (`src/lib/messages/reply.functions.ts`, `requireSupabaseAuth`) inserts the `messages` row + bumps `conversations.last_message_at` via `context.supabase` (the **authed** server-fn client, not admin) → RLS **WITH CHECK** re-validates `client_id` on insert → cannot write cross-tenant. ✓ (Correctly distinct from the cron runner's own message-insert, which runs as service-role under pg_cron — see the message-insert note in F4.)
- **Send-primitive reuse (runbook flag #5) — SATISFIED.** New `src/lib/sms/send.server.ts` is the single send primitive (`sendStubSms` / `sendStubSmsWithRetry`). The cron runner was refactored to import `sendStubSmsWithRetry` (inline stub removed); the reply path imports the **same** `sendStubSmsWithRetry`. **Cron + interactive reply converge on one send path** — exactly the consolidation flag #5 asked for, and the same reuse pattern 2f proved. ✓
- **Conversations tab conformance — MATCH.** List: newest-first by `last_message_at`, contact name + phone + relative time + status badge. Thread: iMessage-style bubbles (outbound right/primary, inbound left/card), back button, reply composer. ✓ Matches mobile-app skill Tab 1 (iMessage-style, newest-first, status badges, relative time, in-thread reply). Route at `/app` (`_authenticated/app.index.tsx`) — consistent with the skill's "exists at `/app`; keep/extend."
