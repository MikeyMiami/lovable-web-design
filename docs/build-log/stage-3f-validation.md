### (original finding) 🔴 CRITICAL — F-resolver: the SMS runner never reads `templates` (pre-existing, latent since 2e)
The override walk exposed it. There are **three readers, two implementations, and the SMS render reads no templates at all:**
| Reader | Override-aware? |
|---|---|
| Notification dispatcher (2c, `write.server.ts:84 loadTemplate`) — `.or(client_id.eq.X, client_id.is.null)` then `find(client_id===X) ?? data[0]` | ✅ |
| Sequence loader (runner `loadStep`/`loadSequenceMeta`, `enroll loadStartDelay`) — same `.or`+prefer-client on `sequences` | ✅ |
| **SMS copy render (`runner.server.ts:437`)** — `body = step.body ?? "[stub] "+templateKey`; **never queries `templates`** | ❌ |

`step.body` is never set (steps_json = `{kind, templateKey, offsetMinutes}` only) → **every outbound drip SMS has emitted the literal `[stub] <key>`, never the template body (global or override).** Consequences:
1. **Real gap, NOT expected stub behavior — confirmed.** "Stub" legitimately means the *transmission* is stubbed (no Twilio call, stub SID); the **body should always be the rendered template copy**. Emitting `[stub] <key>` means the body was never rendered. **At 1f this would transmit `[stub] review_request_sms1` to real customers** (the stub→real-SID swap does NOT touch the body line). Pre-freeze must-fix.
2. **Retroactive scope:** all of Stage 2's drip testing validated send **mechanics** (claim-lease/window/caps/materialization) — NOT message **content**; the bodies were always `[stub]` literals. *(In hindsight this was visible at 3c, where the materialized body was `[stub] missed_call_sms1` — I validated the row mechanics there but did not flag the placeholder body; the override walk is what forced rendering real content and exposed it.)*

### Fix (sound + minimal — with one caveat)
Extract `resolveTemplate(clientId, key)` from `write.server.ts`'s `loadTemplate` into `src/lib/templates/resolve.server.ts`; use it in BOTH the dispatcher AND the runner SMS branch; the runner renders `step.templateKey` → resolved template → `dripMergeVars`. Only the body-render line changes; claim-lease/window/caps/retry/advance untouched. **Sound + minimal.** ✓ Two things to verify in the fix:
- **F-seeded (the possibly-BIGGER issue):** confirm the SMS body templates actually EXIST as seeded global rows in `public.templates` keyed by the step `templateKey`s (`review_request_sms1..4`, `one_year_sms1..5`, `missed_call_sms1..2`, lead-form/discount SMS, etc.). Because the runner never read templates, these may **never have been seeded** (2a seeded sequences + 2c seeded the `*_internal` notification templates — the SMS bodies may be absent). If so, the fix is NOT just "extract a resolver" — it must ALSO **seed the SMS copy from `automation-config`** as global rows, and that's the first validation of the actual customer-facing SMS copy. `SELECT key FROM templates WHERE client_id IS NULL` → must include every SMS step key.
- **F-merge:** confirm the runner's render injects the **per-contact tracked `review_link`** (the token URL `/api/public/r/<token>`) + all SMS merge keys (`first_name`, `company_name`, `review_request_link`, `company_owner_first_name`, `discount__on_referral`, `company_website_link`, `quote_form_link`, …) — not just the notification var set. The review/reactivation SMS is worthless without the tracked link rendered correctly.

### The walk that proves the fix
Edit a `review_request_sms1` override for client A → fire the review drip for A and B → **A's `messages.body` = A's override copy (merged, with the tracked link); B's = the global template copy** — neither is `[stub]`. (+ a `sequences` override if the editor changes steps.) That's the end-to-end proof.
